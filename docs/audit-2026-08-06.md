# Audit Aplikasi - 2026-08-06

Audit ini memakai skill `context-map` di `.agents/skills/` (petakan dulu sebelum mengubah).
Ruang lingkup sengaja dipilih agar **tidak tumpang tindih** dengan audit sebelumnya:

- `docs/audit-2026-08-03.md` menutup temuannya dengan catatan bahwa modul **Belanja/E-commerce,
  Undian, dan Form Builder "tidak diaudit mendalam"**.
- Sesi 2026-08-04 sudah membereskan RBAC, endpoint debug tanpa auth (`/api/debug`,
  `/api/test-waha`), backup deploy, index `form_submissions`, dan overflow mobile.
- Commit `6e2a1f1` baru saja mengeraskan endpoint lead IndiHome (honeypot + konfirmasi WA).

Jadi audit ini masuk ke tiga area yang belum pernah disentuh: **alur pembayaran Belanja,
endpoint submit form publik, dan duplikasi struktural yang tersisa.** Tidak ada satu pun temuan
di bawah yang mengulang isi `audit-2026-08-03.md` atau `docs/session.md`.

Metode: pembacaan kode statis. Mesin ini masih tanpa MySQL server, jadi **tidak ada temuan di
bawah yang diuji runtime** — semuanya dibaca dari alur kode.

> **PEMBARUAN (hari yang sama):** MySQL 8.0 akhirnya bisa dijalankan lewat WSL, dan seluruh
> temuan Kritis di bawah (K1, K2, K3) sudah **dibuktikan dapat dieksploitasi tanpa kredensial
> apa pun** terhadap server dan database hidup. Uji runtime itu juga menemukan satu bug baru
> yang tidak terlihat dari pembacaan statis: **race condition yang membagikan kode voucher yang
> sama ke beberapa pelanggan sekaligus**. Lihat `docs/uji-runtime-2026-08-06.md`.

## Kritis - bypass pembayaran (tiga jalur terpisah)

Ketiganya berada di bawah `/api/public/...`, sehingga matcher middleware
(`/admin`, `/api/admin`, `/portal-admin`) **tidak pernah mencakupnya**. Ini pola persis yang sama
dengan `/api/debug` dan `/api/test-waha` yang dihapus di sesi 2026-08-04 — tiga sisanya lolos
karena bersarang lebih dalam di `/api/public/orders` dan `/api/public/webhook`.

Dampak bersama: `paymentStatus` order menjadi `success` lalu `triggerAutoRedeem()` berjalan.
Auto-redeem **menandai voucher nyata sebagai terpakai** (`vouchers.isUsed = true`) dan menulis
ulang `products.stock`. Jadi walau tidak ada uang yang berpindah, stok voucher benar-benar
terbakar dan pembukuan pesanan jadi salah.

### K1. `POST /api/public/orders/[id]/simulate` - siapa pun bisa menandai order lunas

**File:** `src/app/api/public/orders/[id]/simulate/route.ts`

Komentarnya sendiri berbunyi `// TEMPORARY ENDPOINT FOR TESTING WITHOUT REAL LYNK.ID`. Tidak ada
pengecekan sesi, tidak ada secret, tidak ada pembatasan environment. Cukup tahu (atau menebak)
sebuah order id, lalu POST ke endpoint itu, dan order langsung `success`.

Sudah disisir: **tidak ada satu pun pemanggil** di `src/` (satu-satunya hit kata "simulate"
lainnya adalah komentar tak terkait di `src/app/(hidden)/form-undian/page.tsx:316`). Ini murni
sisa development, sama seperti `/api/test-waha` dulu.

Rekomendasi: **hapus filenya**, jangan dipagari. Lynk.id sudah lama digantikan (lihat K4).

### K2. Webhook Mayar tidak memverifikasi apa pun

**File:** `src/app/api/public/webhook/mayar/route.ts`

Ini gateway pembayaran yang aktif (doku dan lynkid sudah jadi tombstone 410, lihat K4). Handler
langsung `await request.json()` lalu percaya isinya. Tidak ada HMAC, tidak ada signature, tidak
ada token header, tidak ada allowlist IP — `grep` untuk `createHmac|createHash|signature` di file
ini nihil.

Siapa pun yang mengirim body ini ke endpoint publik akan mendapat order lunas:

```json
{ "event": "payment.received", "data": { "id": "<invoiceNumber>", "status": true } }
```

`invoiceNumber` adalah satu-satunya yang perlu diketahui, dan nilainya dipegang pembeli sendiri
dari alur checkout — jadi pembeli sah pun bisa melunasi pesanannya sendiri tanpa membayar.

Rekomendasi: verifikasi signature webhook Mayar sebelum menyentuh database. Bila Mayar
menyediakan header signature, cocokkan dengan HMAC dari raw body (`await request.text()`, bukan
`.json()`, karena HMAC harus atas byte mentah). Bila Mayar tidak menyediakannya sama sekali,
minimal wajibkan shared secret di query/header yang dibandingkan dengan
`crypto.timingSafeEqual`, dan verifikasi ulang status pembayaran ke API Mayar sebelum menandai
lunas.

### K3. Verifikasi signature Midtrans bisa dilewati dengan menghilangkan field-nya

**File:** `src/app/api/public/webhook/midtrans/route.ts:49`

```ts
const config = await getMidtransConfig();
if (config && signature_key) {
    // ... verifikasi, 403 bila gagal
}
// jalan terus ke update order
```

Verifikasi dibungkus `if`, dan **kegagalan mendapatkan prasyaratnya berarti lolos**, bukan
ditolak. Dua cara melewatinya:

1. Kirim body **tanpa** `signature_key` — kondisi `signature_key` falsy, blok dilompati.
2. `getMidtransConfig()` mengembalikan `null` bila `midtrans_server_key` belum diisi di
   `site_settings` (`src/lib/midtrans.ts:58`) — dalam kondisi itu semua webhook diterima mentah.

Verifikasi signature harus fail-closed. Rekomendasi: bila `config` tidak ada atau `signature_key`
tidak ada, balas 403 dan berhenti — jangan lanjut ke update order.

### K4. Rantai deprecation gateway pembayaran menunjuk ke tempat yang salah

**File:** `src/app/api/public/webhook/doku/route.ts`, `.../lynkid/route.ts`

- `lynkid` berkata: *"replaced by /api/public/webhook/doku"*
- `doku` berkata: *"replaced by /api/public/webhook/mayar"*

Jadi petunjuk di `lynkid` sudah basi satu generasi — mengarahkan integrator ke endpoint yang
juga sudah mati. Keduanya hanya mengembalikan 410 dan komentarnya sendiri bilang
*"kept only until the directory can be cleaned up"*.

Tiga provider (`doku`, `lynkid`, `midtrans`) menganggur sementara hanya `mayar` yang hidup, plus
`src/lib/doku.ts`, `src/lib/mayar.ts`, `src/lib/midtrans.ts` yang semuanya masih ikut ter-build.
Ini bentuk tumpang tindih yang paling terlihat di repo ini.

Rekomendasi: putuskan satu gateway resmi, hapus tombstone `doku`/`lynkid` beserta `src/lib/doku.ts`.
Bila Midtrans memang masih rencana dipakai, perbaiki K3 dulu; bila tidak, hapus sekalian.

## Tinggi - endpoint submit form publik tanpa rem sama sekali

**File:** `src/app/api/forms/[formId]/submit/route.ts` (199 baris)

Ini pintu masuk peserta Undian. Tidak ada rate limit, tidak ada honeypot, tidak ada validasi
asal request — `grep` untuk `rateLimit|honeypot|ip|headers` di file ini nihil.

Yang membuatnya lebih dari sekadar spam data:

- Handler ini **menulis file ke disk** (`writeFile`, `mkdir` dari `fs/promises`) untuk field
  upload.
- Handler ini **mengirim WhatsApp** lewat gateway perusahaan
  (`sendTemplatedWhatsApp`, `DEFAULT_UNDIAN_TEMPLATE`).

Artinya satu skrip loop terhadap endpoint publik ini bisa mengisi disk VPS sekaligus menghabiskan
kuota/reputasi nomor WA perusahaan — konsekuensi yang sama persis dengan alasan `/api/test-waha`
dihapus di sesi 2026-08-04.

Yang menonjol: endpoint lead IndiHome **sudah** punya honeypot, normalisasi nomor, dan rate limit
per IP dan per nomor (dicatat di `docs/session.md`, dikeraskan lagi di commit `6e2a1f1`).
Perlindungan itu tidak pernah dibawa ke endpoint form Undian, padahal profil risikonya identik
dan volumenya lebih besar.

Rekomendasi: pakai ulang pola yang sudah terbukti di endpoint IndiHome — rate limit per IP dan
per nomor WA, plus honeypot — jangan tulis mekanisme ketiga yang berbeda lagi.

## Sedang

### S1. Dua route penyaji upload yang sudah menyimpang diam-diam

**File:** `src/app/api/public/uploads/[filename]/route.ts` dan
`src/app/api/public/uploads/[...filename]/route.ts`

Dua handler nyaris identik di direktori yang sama. Next.js memberi prioritas ke `[filename]`
untuk path satu segmen, sehingga `[...filename]` praktis hanya melayani path bersarang seperti
`submissions/foo.jpg`.

Duplikasi itu sudah menghasilkan drift nyata: versi `[filename]` memetakan `ico` ke
`image/x-icon`, versi catch-all **tidak**. Jadi favicon `.ico` yang tersimpan di subfolder
disajikan sebagai `application/octet-stream` dan tidak dirender browser — padahal `.ico` termasuk
tipe yang diizinkan oleh endpoint upload admin.

Rekomendasi: pertahankan hanya `[...filename]` (ia mencakup kedua kasus), salin peta
content-type yang lebih lengkap ke sana, hapus `[filename]`.

### S2. SVG yang diizinkan naik lalu disajikan same-origin = stored XSS

**File:** `src/app/api/admin/upload/route.ts:33` dan kedua route penyaji di atas

`allowedTypes` memuat `image/svg+xml`, dan route penyaji mengembalikannya dengan
`Content-Type: image/svg+xml`. SVG bisa memuat `<script>`, dan karena disajikan dari origin yang
sama dengan panel admin, skrip itu berjalan dengan sesi admin yang sedang membukanya.

Dua hal yang memperlemah gerbangnya:

- `if (file.type && !allowedTypes.includes(file.type))` — cek dilewati sepenuhnya bila `file.type`
  string kosong.
- Ekstensi diambil dari nama file kiriman (`file.name.split(".").pop()`), bukan diturunkan dari
  tipe yang sudah divalidasi.

Ini butuh akses admin (peran serendah `ADMIN_INPUT` sudah cukup), jadi bukan kritis — tetapi
artinya admin berperan rendah bisa mencuri sesi Admin Super.

Rekomendasi: tolak `file.type` kosong alih-alih melewatinya; turunkan ekstensi dari tipe MIME yang
sudah divalidasi; dan sajikan berkas unggahan dengan
`Content-Security-Policy: default-src 'none'` + `Content-Disposition: attachment` untuk SVG (atau
buang SVG dari allowlist bila tidak benar-benar dibutuhkan).

### S3. `auto-redeem` masih simulasi penuh tetapi menghabiskan voucher sungguhan

**File:** `src/lib/auto-redeem.ts:59-75`

Jalur "Telkomsel Redemption Bot" di produksi berisi `await new Promise(r => setTimeout(r, 5000))`
dan `const isSuccess = Math.random() > 0.02` — tidak ada panggilan vendor sama sekali, hanya
`console.log`. Namun cabang suksesnya **melakukan efek samping nyata**: menandai voucher terpakai,
menulis `redemptionLogs` dengan `telkomselTrxId` karangan, dan menimpa `products.stock`.

Jadi 2% pesanan gagal karena lemparan dadu, bukan karena kondisi nyata, dan log redemption berisi
respons vendor yang dibuat-buat namun terlihat asli saat dibaca ulang nanti.

Modul Belanja saat ini **tidak tertaut dari navbar** (`src/components/navbar.tsx:21` — link
"BELANJA" dikomentari sejak sesi 2026-08-03), jadi ini belum menyakiti pengguna. Tapi ia tetap
hidup di level API, dan itulah yang membuat K1-K3 di atas bisa dijangkau.

Rekomendasi: putuskan status modul Belanja secara eksplisit. Bila belum siap, matikan endpoint
publiknya (bukan hanya link navbar-nya). Bila dilanjutkan, ganti blok simulasi dengan integrasi
nyata dan buang `Math.random()` beserta `setTimeout` — jangan sampai ikut terdeploy.

## Rendah - kerapian

### R1. `src/lib/db.ts` adalah re-export mati

Isinya satu baris: `export { db } from "@/db";`. Disisir ke seluruh `src/`: **nol importir** —
79 file mengimpor langsung dari `@/db`. Sisa dari masa sebelum konsolidasi. Rekomendasi: hapus.

### R2. Tiga modul `indihome-*` dengan pembagian peran yang tidak jelas dari namanya

`src/lib/indihome-data.ts` (baca DB + fallback), `indihome-products.ts` (konstanta seed/fallback),
`indihome-admin.ts` (status lead). Pembagiannya sebenarnya sah dan sudah didokumentasikan di
header `indihome-products.ts`, tapi namanya tidak mencerminkannya — `indihome-products.ts`
sekarang justru berisi lokasi, bukan produk. Bukan bug; catat saja bila suatu saat ada penamaan
ulang.
